# Coupon Service

동시 쿠폰 발급에서 Redis Lua 선점으로 실패 요청의 DB 진입과 락 경합을 줄이고, DB 조건부 UPDATE로 최종 재고를 원자적으로 차감하는 쿠폰 발급 서비스입니다.

- 개발 기간: 2026.04.16 ~ 2026.05.10
- 개발 인원: 개인 프로젝트

## 기술 스택

- Java 17
- Spring Boot 4.0.5
- Spring Data JPA
- Spring Data Redis
- OpenFeign QueryDSL 5.6.1
- MySQL
- Redis
- Gradle
- JUnit 5

## 주요 기능

- 쿠폰 이벤트 생성·조회와 만료 이벤트 종료 처리
- Redis Lua 기반 쿠폰 발급, 중복 발급 방지 및 재고 보상
- 쿠폰 사용과 사용 이력 관리
- 사용 가능한 사용자 쿠폰 조회
- 관리자 재동기화로 Redis/DB 발급 상태 복구

## 문제와 개선

초기 구조는 쿠폰 이벤트 row에 DB 비관적 락을 획득한 뒤 재고를 차감하고 발급 이력을 저장했습니다. 재고 정합성은 지킬 수 있었지만, 동일 이벤트로 동시 요청이 몰리면 요청들이 하나의 row 락을 기다리며 지연됐습니다.

현재 구조는 Redis Lua Script로 발급 기간·중복·재고를 원자적으로 확인하고 재고를 선점한 뒤, 성공한 요청만 DB 처리 경로로 전달합니다. DB에서는 `remainingQuantity > 0` 조건부 UPDATE로 최종 재고를 차감하고 발급 이력을 저장합니다.

| 구분 | 초기 구조 | 개선 구조 |
| --- | --- | --- |
| 사전 검증 | DB 쿠폰 이벤트 row 비관적 락 | Redis Lua Script 원자 선점 |
| DB 재고 차감 | 락 획득 후 재고 차감 | `remainingQuantity > 0` 조건부 UPDATE |
| 거절 요청 | DB 처리 경로에 포함 | DB 조회, UPDATE, INSERT를 수행하지 않음 |
| 최종 기록 | DB 발급 이력 저장 | DB 발급 이력 저장 |

## 쿠폰 발급 흐름

1. Redis Lua Script가 발급 상태 초기화 여부, 발급 기간, 중복 발급, 재고를 확인합니다.
2. Lua Script가 재고 차감과 발급 사용자 등록을 하나의 원자 연산으로 수행합니다.
3. Redis 선점에 성공한 요청만 사용자와 쿠폰 이벤트를 조회합니다.
4. `remainingQuantity > 0` 조건부 UPDATE로 DB 재고를 차감합니다.
5. 쿠폰 발급 이력을 INSERT합니다.
6. DB 커밋에 성공하면 Redis 선점을 유지합니다. 일반적인 롤백에서는 Redis 재고와 발급 사용자 정보를 원복하며, 재고 불일치·DB 중복 제약 위반·트랜잭션 결과 불명확·보상 실패가 발생하면 재동기화 대기 상태로 전환합니다.

## 실패 보상과 재동기화

DB 재고 차감 결과가 Redis 선점 결과와 다르거나 중복 제약 위반, 트랜잭션 결과 불명확, Redis 보상 실패가 발생하면 해당 이벤트를 재동기화 대기 상태로 전환해 추가 발급을 차단합니다. 이후 관리자 재동기화 API가 DB 발급 이력을 기준으로 Redis 재고와 발급 사용자 정보를 재구성한 뒤 발급을 재개합니다.

## 성능 및 부하 검증

### 로컬 성능 비교

동일한 로컬 환경과 nGrinder 설정에서 DB 비관적 락 구조와 Redis Lua 선점·DB 조건부 재고 차감 구조를 비교했습니다.

| 항목 | DB 비관적 락 구조 | Redis Lua 선점·DB 조건부 재고 차감 구조 |
| --- | ---: | ---: |
| 1,000 VUser 평균 응답 시간 | 2,378ms | 약 240ms |
| 응답 시간 변화 | - | 약 90% 감소 |
| 1,000 VUser 평균 TPS | 약 249 | 약 597 |
| TPS 변화 | - | 약 2.4배 |

- DB 비관적 락 구조는 1,000 VUser까지 정상 처리됐고, 1,500 VUser 이상에서 지연과 실패가 증가했습니다.
- 개선 구조는 1,000~4,000 VUser의 기록된 모든 회차를 완료했습니다.
- 5,000 VUser는 2/3회, 6,000 VUser는 3/4회, 7,020 VUser는 1/3회 완료했습니다.

### AWS 다중 인스턴스 배포 검증

클라우드 배포 경험을 쌓고, ALB·애플리케이션 EC2 2대·RDS·ElastiCache로 구성한 AWS 환경에서 동시 발급 동작과 부하 증가 양상을 확인했습니다.

<img src="assets/coupon-deploy-aws.png" alt="AWS 부하 테스트 아키텍처" width="900">

| 항목 | 검증 환경 및 결과 |
| --- | --- |
| 요청 경로 | AWS nGrinder -> ALB -> App EC2 2대 -> RDS MySQL / ElastiCache Redis |
| App EC2 | `c8i.xlarge` 2대 |
| nGrinder EC2 | `c8i.xlarge` 1대 |
| RDS | MySQL `db.m7g.large` |
| Redis | ElastiCache Redis `cache.t4g.medium` |
| 검증 구간 | 1,000~9,000 VUser |
| 9,000 VUser | 3/3회 정상 판정 |
| 10,000 VUser | nGrinder 서버 메모리 부족으로 중단 |

로컬과 AWS는 인프라와 부하 조건이 달라 응답 시간이나 TPS를 비교하지 않았습니다.

### 발급 상태 검증 기준

로컬과 AWS 모두 DB 발급 수, Redis 발급 사용자 수, DB·Redis 잔여 재고와 nGrinder 오류 수를 교차 확인해 정상 회차를 판정했습니다.

```text
DB 발급 이력 수 = 목표 발급 수
Redis 발급 사용자 수 = 목표 발급 수
DB 잔여 재고 = 0
Redis 잔여 재고 = 0
nGrinder 오류 수 = 0
```

정상 판정 회차에서는 DB와 Redis의 발급 수·잔여 재고가 목표 상태와 일치했습니다.

### 결과

| 구분 | 결과 |
| --- | --- |
| 로컬 성능 비교 | 동일한 로컬 환경의 1,000 VUser에서 평균 응답 시간이 `2,378ms -> 약 240ms`로 약 90% 감소했습니다. 평균 TPS는 비관적 락 구조 약 249, 개선 구조 약 597로 약 2.4배 향상됐습니다. |
| 로컬 부하 확인 | 개선 구조는 1,000~4,000 VUser의 기록된 모든 회차를 완료했습니다. 5,000 VUser 이상에서는 일부 회차에 미완료 요청이 발생했으며, 원인은 분리하지 못했습니다. |
| AWS 배포 검증 | 다중 인스턴스 환경에서 9,000 VUser를 3/3회 정상 판정했습니다. 10,000 VUser는 nGrinder 서버 메모리 부족으로 중단돼 애플리케이션의 처리 한계는 측정하지 못했습니다. |
| 발급 상태 검증 | 정상 판정 회차에서 DB와 Redis의 발급 수·잔여 재고가 목표 상태와 일치했습니다. |
| 병목 분석 | 부하 증가 시 RDS Connection 사용량과 ALB 대상 응답 시간이 함께 상승해 최종 DB 저장 구간을 병목 후보로 판단했습니다. SQL 지연·DB CPU·lock wait를 분리 측정하지 않아 원인을 확정하지는 않았습니다. |

## 테스트

주요 테스트 범위는 다음과 같습니다.

- 쿠폰 이벤트 생성과 Redis 발급 상태 초기화
- 쿠폰 이벤트 생성 요청 validation
- Redis 초기화 실패 시 재동기화 대기 처리
- 쿠폰 이벤트 조회 및 만료 이벤트 종료 처리
- 쿠폰 발급의 정상·실패·동시성 시나리오
- 쿠폰 사용의 정상·실패·동시성 시나리오
- 사용자 쿠폰 조회 조건과 할인율 계산
- Redis/DB 재고 재동기화 및 보상 복구
